# F6 — Worker + Workers AI

**Proyecto:** `docs/app-compatibilidad-ia.md`
**Issue:** #11
**Rama base:** `claude/ai-model-compatibility-plan-ptlr3j`
**Depende de:** F1, F2

## Objetivo

La capa de IA, que es **enteramente opcional**: si se cae, si se agota la cuota o si el usuario está sin red, la app sigue funcionando igual. La IA traduce lenguaje a datos y datos a lenguaje; **ningún número del veredicto sale de ella**.

## Contrato de entrada

- `src/lib/hardware/types.ts` (F0) — `SystemSpecs` es el objeto que cruza cliente ↔ Worker.
- `resolveGpu` y `estimate` (F2), que el Worker importa igual que el cliente.
- `src/data/hardware/gpus.json` (F1), que el Worker embebe para reconciliar la salida del modelo.

## Contrato de salida

- Un Worker que sirve `/api/hw/*` y delega **todo lo demás** a `env.ASSETS`.
- Tres endpoints, todos degradables: `{ ok: false, reason }` ante cualquier fallo, y el cliente sigue en local.

## Archivos que posee

- `worker/index.ts` (nuevo) — enrutado y delegación a assets
- `worker/ai.ts` (nuevo) — prompts, esquemas JSON y la constante `MODEL`
- `wrangler.jsonc` (editar)
- `src/components/hardware/app.ts` (editar) — **solo** el enganche opcional a los endpoints
- `.github/workflows/deploy.yml` (editar, si hace falta para el binding)

## PROTEGIDOS

- `src/lib/hardware/estimate.ts`
- `src/lib/hardware/resolve.ts`

## Instrucciones

### El cambio en `wrangler.jsonc`

Pasa de "solo assets" a Worker con assets:

```jsonc
{ "name": "fuenteai",
  "main": "worker/index.ts",
  "compatibility_date": "2026-06-18",
  "assets": { "directory": "./dist", "binding": "ASSETS",
              "html_handling": "drop-trailing-slash", "not_found_handling": "404-page" },
  "ai": { "binding": "AI" },
  "kv_namespaces": [{ "binding": "HW_CACHE", "id": "…" }] }
```

El `fetch` del Worker: si el `pathname` empieza por `/api/`, enruta; si no, `return env.ASSETS.fetch(request)`. **Las 86 fichas y toda la navegación tienen que servirse exactamente igual que antes.** Verificalo con `wrangler dev` antes de considerar la fase hecha: este es el único cambio del proyecto que puede romper el sitio en producción.

### Los tres endpoints

Todos `POST`, todos con `response_format: { type: 'json_schema', json_schema: … }` (JSON mode de Workers AI).

| Ruta | Entrada | Salida | Papel |
|---|---|---|---|
| `/api/hw/parse` | texto libre (≤ 1 KB) | `SystemSpecs` parcial + `confidence` + `unknownFields[]` | Traduce lenguaje a datos. **La salida se reconcilia contra `gpus.json` en el servidor**: si la GPU está en la base, la VRAM que diga el modelo se descarta y gana la base. |
| `/api/hw/gpu-lookup` | nombre de GPU sin coincidencia | `{ vramGb, bandwidthGbs, vendor, year, confidence }` | Solo para GPUs fuera de la base. Se cachea en KV 30 días por nombre normalizado. El cliente lo muestra **siempre etiquetado "estimado por IA"**. |
| `/api/hw/explain` | veredicto ya calculado + specs + `lang` | 2–3 frases + 2 consejos | Solo redacta. **Recibe los números hechos; no los calcula ni los corrige.** |

### Elección de modelo

Fijá el id en **una única constante** `MODEL` en `worker/ai.ts`. **Verificá el catálogo vigente en `developers.cloudflare.com/workers-ai/models` en el momento de implementar** — no uses un id de memoria, la lista cambia. Criterio de elección: el modelo más pequeño con soporte de salida estructurada que pase los casos de parseo. El trabajo es extracción, no razonamiento.

### Prompts

Versionados en `worker/ai.ts`, con instrucción explícita de **extraer, no inferir**: si el usuario no dijo su RAM, el campo va `null`, nunca un valor inventado. Un dato inventado aquí contamina un veredicto que el usuario cree calculado.

Timeout de 6 s. Ante cualquier fallo, `{ ok: false, reason }` y el cliente continúa con el resolver local.

## Fuera de alcance

- Límite de peticiones, caché y cabeceras de seguridad (F7). Dejá los puntos de enganche.
- Cambiar el motor de cálculo o los datos.
- Que la IA emita veredictos: nunca, en ninguna fase.

## Criterios de aceptación

- [ ] `npx wrangler deploy --dry-run` sale 0
- [ ] `npm run build` sale 0
- [ ] `grep -c "env.ASSETS.fetch" worker/index.ts` devuelve un número mayor que 0
- [ ] `grep -rE "response_format" worker/ai.ts` devuelve al menos 3 líneas (los tres endpoints)
- [ ] `[manual]` Con `npx wrangler dev`: la portada, una ficha y una página de categoría se sirven idénticas a producción.
- [ ] `[manual]` Con `npx wrangler dev`: los tres endpoints responden JSON válido contra el esquema declarado.
- [ ] `[manual]` **Prueba de degradación:** bloquear `/api/*` en las DevTools y recorrer la app entera. Todo funciona, sin errores en consola, solo sin la prosa de la IA.
- [ ] `[manual]` 15 frases de prueba (5 en cada idioma) parsean a `SystemSpecs` correctos.

## Riesgos conocidos

- **Romper el sitio en producción.** Es el riesgo mayor de todo el proyecto: `deploy.yml` despliega en cada push a `main`. Por eso todo va a la rama de integración y `wrangler dev` es criterio de aceptación, no una cortesía.
- **Que la IA se vuelva camino crítico.** Si el cliente espera la respuesta del Worker antes de mostrar resultados, una caída de Workers AI se convierte en una caída de la app. El resultado local se pinta primero y la prosa de la IA llega después.
- **Alucinación de VRAM.** Por eso se reconcilia contra `gpus.json` en el servidor y lo estimado se etiqueta como tal.
- **Coste.** Cada llamada consume cuota. F7 añade caché y límites; hasta entonces, no lo dejes activo en un despliegue público.
