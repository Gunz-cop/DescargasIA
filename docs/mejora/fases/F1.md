# F1 — Medición de comportamiento y funnel hacia fuentes oficiales

**Proyecto:** `docs/plan-mejora-productos-por-idioma.md`
**Issue:** #36
**Producto:** `común`
**Rama base:** no especificada en #36; Codex debe declarar una rama de integración antes del PR
**Depende de:** F0 (#35) — gobierno, baseline y contratos

## Objetivo

Poder distinguir adquisición desde Google, lectura de ficha, selección de plataforma, entrada a `/r` y salida hacia el canal oficial, sin mezclar productos lingüísticos ni recopilar PII. La instrumentación se diseña para que F7 pueda decidir el proveedor o formato de medición sin reescribir los call sites.

## Contrato de entrada

- F0 está cerrado: baseline, decisiones y matriz de propietarios existen.
- `docs/mejora/baseline.md` conserva los periodos y resultados de Google Search Console y Cloudflare Web Analytics.
- `docs/mejora/decisiones.md` registra que el proveedor y formato de medición son una decisión abierta de F1.
- No existe instrumentación de eventos en el repositorio; no hay dependencias de analítica externa.
- `/r` es un interstitial client-side, `noindex`, bloqueado en robots.txt y excluido del sitemap.
- El catálogo `tools-base` contiene `officialWebsite` y `platforms` con `isOfficial` para cada herramienta.

Si falta la baseline o la definición del issue, la fase se bloquea. No se inventa un proveedor para desbloquearla.

## Contrato de salida

## Esquema de eventos

### Eventos

| Nombre | Dispara Cuando | Call site |
|---|---|---|
| `ficha_view` | La persona carga una ficha de herramienta | `[lang]/[slug].astro` |
| `platform_select` | La persona hace clic en un botón de plataforma dentro de la ficha | `[lang]/[slug].astro` (event listener en `<script>`) |
| `redirect_start` | Se carga el interstitial `/r` con parámetros válidos | `/r/index.astro` |
| `redirect_result` | El timer de `/r` completa y se inicia la redirección | `/r/index.astro` |
| `redirect_error` | `/r` detecta parámetros inválidos o工具a/plataforma no encontrado | `/r/index.astro` |

### Parámetros comunes

Todos los eventos incluyen estos campos:

| Parámetro | Tipo | Valores permitidos | Descripción |
|---|---|---|---|
| `event` | `string` | `ficha_view`, `platform_select`, `redirect_start`, `redirect_result`, `redirect_error` | Nombre del evento |
| `lang` | `string` | `es`, `sv`, `it` | Idioma/producto del sitio |
| `tool` | `string` | slug alfanumérico con guiones (del catálogo) | Identificador de la herramienta |
| `platform` | `string \| null` | `web`, `windows`, `mac`, `linux`, `android`, `ios` o `null` | Plataforma seleccionada |
| `channel` | `string` | `official-website`, `app-store`, `github-repo`, `package-manager`, `documentation`, `official-installer`, `web-app` | Tipo de canal oficial |

### Parámetros por evento

| Evento | Parámetros adicionales |
|---|---|
| `ficha_view` | `platform` es la plataforma principal (la primera disponible) |
| `platform_select` | `platform` es la plataforma clickeada |
| `redirect_start` | `platform` es la plataforma del interstitial; incluye `valid: true` |
| `redirect_result` | `platform` es la plataforma redirigida; incluye `valid: true` |
| `redirect_error` | `platform` es `null`; incluye `valid: false` y `reason` (código controlado: `tool_not_found`, `platform_not_found`, `not_official`, `missing_params`) |

### Ejemplo de payload

```json
{
  "event": "ficha_view",
  "lang": "es",
  "tool": "chatgpt",
  "platform": "web",
  "channel": "web-app"
}
```

```json
{
  "event": "redirect_error",
  "lang": "sv",
  "tool": "herramienta-inexistente",
  "platform": null,
  "channel": "unknown",
  "valid": false,
  "reason": "tool_not_found"
}
```

### Restricciones de privacidad

Los parámetros **nunca** incluyen:

- Texto libre de búsqueda ni consultas del usuario.
- IP, correo electrónico ni identificadores persistentes.
- URLs arbitrarias introducidas por el usuario.
- Datos de geolocalización.
- User-Agent completo ni fingerprints.

Los parámetros **solo** incluyen identificadores controlados derivados del catálogo (`tool`, `platform`, `lang`, `channel`) o códigos de error predefinidos (`reason`).

### Proveedor de medición

F1 **no instala** un proveedor de analítica externo. El módulo `funnel-events.ts`:

1. Construye el payload validado.
2. Lo despacha como `CustomEvent` en `window` (para que cualquier consumidor futuro lo escuche).
3. Permite registrar un handler externo mediante `onFunnelEvent()` para cuando F7 o Codex decidan el proveedor.

Esta decisión está registrada en `docs/mejora/decisiones.md` como pendiente.

## Instrucciones

1. Crear `src/utils/funnel-events.ts` con:
   - Tipos TypeScript para cada evento y sus parámetros permitidos.
   - `VALID_LANGS`, `VALID_PLATFORMS`, `VALID_CHANNELS` como arrays de literales.
   - `validatePayload()` que rechace valores fuera de enumeración.
   - `stripPII()` que verifique que no hay campos prohibidos.
   - `dispatchFunnelEvent()` que construya, valide y despache como `CustomEvent`.
   - `onFunnelEvent()` para registro de handlers externos (vacío por defecto).
   - `FUNNEL_EVENT_NAMES` exportado para tests.

2. Crear `tests/funnel/events.test.mjs` con:
   - Test de que cada nombre de evento válido es aceptado.
   - Test de que un nombre de evento inválido es rechazado.
   - Test de que `lang` inválido es rechazado.
   - Test de que `platform` inválida es rechazada.
   - Test de que `channel` inválido es rechazado.
   - Test de que un campo libre de texto no se incluye en el payload.
   - Test de que los parámetros `reason` en `redirect_error` son solo los predefinidos.

3. Crear `tests/funnel/no-pii.test.mjs` con:
   - Test que audita `src/utils/funnel-events.ts` y verifica que no hay llamadas a `fetch()`, `navigator.sendBeacon()`, `XMLHttpRequest`, `document.cookie`, `localStorage.setItem`, ni escritura a bases de datos.
   - Test que verifica que los campos del payload son solo los declarados en el esquema (no acepta campos adicionales).

4. Añadir a `src/pages/[lang]/[slug].astro` un `<script>` (no `is:inline`) que:
   - Emita `ficha_view` al cargar (con `lang`, `tool.slug`, plataforma principal, canal principal).
   - Escuche clics en los botones de plataforma y emita `platform_select`.

5. Añadir a `src/pages/r/index.astro` (dentro del `<script is:inline>` existente):
   - `redirect_start` cuando la validación es exitosa y se muestra el contenido.
   - `redirect_result` cuando el timer completa y se llama a `window.location.replace`.
   - `redirect_error` cuando la validación falla.
   - Los payloads se construyen con los datos ya disponibles en ese scope (`toolId`, `platformId`, `lang`, `tool`, `targetUrl`).

6. Investigar el pico del 2026-08-25: el baseline documenta un pico aproximado de 100 visitas pero no contiene el desglose por ruta, referente, agente ni parámetros. Sin acceso al dashboard de Cloudflare, la investigación no es reproducible. Documentar esta limitación en la spec.

7. Ejecutar `npm test` y `npm run build` al final.

## Riesgos conocidos

- **Proveedor no decidido.** El esquema está diseñado para ser consumido por cualquier proveedor futuro. Si F7/Codex decide un formato diferente, solo cambia el handler registrado en `onFunnelEvent()`, no los call sites.
- **Cloudflare sin desglose por ruta.** El pico del 2026-08-25 no puede investigarse sin acceso al dashboard. F1 documenta esta limitación; la instrumentación permite que futuros picos sí se puedan atribuir.
- **Client-side en `/r`.** Todos los scripts de `/r` son `is:inline` y dependen de `window`. El módulo `funnel-events.ts` se consume como tipos y funciones TypeScript que se inyectan en el inline script; no hay dependencia de bundler en runtime.
- **Volumen bajo.** Con 370 visitas en el periodo baseline, los eventos de funnel serán escasos. La instrumentación es útil para detectar errores y patrones, no para estadísticas significativas hasta que el tráfico crezca.
