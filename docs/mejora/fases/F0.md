## Objetivo

Dejar el contrato documental de la mejora por producto lingüístico listo para
que una sesión limpia pueda ejecutar las fases siguientes sin depender de una
conversación anterior. F0 fija la baseline disponible, los límites entre
`es`, `sv`, `it` y común, y las reglas de propiedad de archivos.

## Contrato de entrada

- Existe el plan maestro en `docs/plan-mejora-productos-por-idioma.md`.
- El issue #35 define F0 como gobierno, baseline y contratos.
- El repositorio puede tener cambios no relacionados; no se sobrescriben.

  `.claude/skills/sdd-fases/`.

  maestro; los exports originales no forman parte del checkout.

Si falta el plan maestro o la definición del issue, la fase queda bloqueada.
No se reconstruyen exports ni se inventan filtros para desbloquearla.

## Instrucciones

1. Lee el plan maestro como spec de producto y conserva sus decisiones de
   independencia lingüística. No cambies su contenido preexistente como parte
   de este issue.
2. Copia en `baseline.md` únicamente los datos declarados por el plan. Separa
   periodo, fuente, filtros conocidos, definiciones y limitaciones. Cuando un
   filtro no esté conservado, escribe que no está disponible.
3. Registra en `decisiones.md` las decisiones cerradas y las abiertas. Las
   decisiones abiertas deben tener responsable y fase bloqueada; no se
   resuelven con un proveedor, país, URL, credencial o rama inventados.
4. Mantén la matriz de archivos disjunta. Una fase no puede poseer un archivo
   que figure en sus propios protegidos ni editar el producto de otro idioma.
5. Mantén el estado operativo en GitHub. Las tablas documentales describen
   propiedad y dependencia, nunca el estado actual de un issue.
6. La plantilla de issue debe apuntar a la spec, duplicar solo la checklist
   que GitHub necesita y exigir PR contra una rama de integración declarada.
7. La plantilla de spec debe conservar todas las secciones obligatorias y
   exigir criterios ejecutables o manuales reproducibles. No uses criterios de
   contar cadenas ni de ausencia por `grep`.

## Riesgos conocidos

- **Exports ausentes.** El baseline no permite recuperar filtros que no quedaron
  en el plan. Se marca cada hueco y F1 debe regenerar el export antes de
  comparar dimensiones no preservadas.
- **Rama de integración no fijada.** El checkout solo demuestra que `main` es
  la base disponible; Codex debe declarar la rama de integración antes de
  abrir PRs de las fases posteriores.
- **Solapamiento de archivos.** Si una fase posterior necesita un archivo
  protegido, se detiene y corrige su spec antes de editar.
- **Deriva de estado.** No se añade una columna de estado a los documentos;
  GitHub sigue siendo la fuente operativa.
- **Confundir señal con causalidad.** `/r`, visitas sin referente y el pico del
  25 de agosto son señales que F1 debe desglosar; no son conversiones ni
  atribuciones confirmadas.
